# Existing chosen project

Keep the user's selected project and existing CLI configuration. This route creates a dedicated connector identity inside that project only when authorized; it does not reuse an unrelated account, link billing, or change existing identities. Use `gcloud projects list --account="$HUMAN_ACCOUNT" --format=json` to establish available projects without setting a default. Zero projects routes to the authorized new-project branch rather than asking the attendee to create one manually.

Before provisioning, privately record the original configuration path (`gcloud info --format='value(config.paths.global_config_dir)'`), active configuration, account, and project. Inspect only presence of authentication overrides and endpoint overrides; unexpected overrides stop for review. Preserve ADC. Keep this provisioning context separate from the isolated runtime described below.

All provisioning commands run in that original credential store with `--account="$HUMAN_ACCOUNT" --project="$PROJECT_ID" --configuration="$ORIGINAL_CONFIGURATION"`. These flags are mandatory even when the current defaults appear correct. Never run `gcloud config set account/project` in the original configuration.

1. Enable `iam.googleapis.com` using `gcloud services enable iam.googleapis.com` with the provisioning flags. If organization policy or permissions block it, preserve the project and explain the gate.
2. Check the intended `claude-assistant@${PROJECT_ID}.iam.gserviceaccount.com`. An existing account without verified connector ownership is a collision, not an idempotent resume. Preserve it; choose a new dedicated name within the authorized setup or review ownership. Create the new account with `gcloud iam service-accounts create <name>` and a clear display name/description, using the provisioning flags.
3. Inspect the exact account's project bindings. Unexpected preexisting roles stop for review; do not remove them. Bind project Viewer with `gcloud projects add-iam-policy-binding "$PROJECT_ID" --member="serviceAccount:$SA_EMAIL" --role=roles/viewer --condition=None` plus provisioning flags. If an existing-project user explicitly needs writes, select appropriate predefined roles for those operations; the prior basic Editor route requires explicit scope and is not necessary for setup. Never grant Owner or IAM administration to complete the test.
4. Reserve a new mode-700 connector directory without overwriting any existing path. Under umask 077, create one key at a nonexistent filename using `gcloud iam service-accounts keys create <new-path> --iam-account="$SA_EMAIL"` plus provisioning flags. The command can truncate existing files before contacting IAM. Refuse existing files and symlinks, preserve failures, and never delete an old key to recover from the key limit.
5. Parse the key privately: require service-account type, exact client email/project ID, and nonempty key material/ID. Check mode 600; print only booleans. Do not echo key JSON.
6. Create a new mode-700 `cli/` directory. In a separate process environment, remove inherited SDK authentication/account/project/configuration and endpoint overrides, set `CLOUDSDK_CONFIG` to this directory, then run `gcloud auth activate-service-account "$SA_EMAIL" --key-file=<new-path> --project="$PROJECT_ID"`. This operation must never use the original CLI directory.
7. In that isolated configuration, require the stored active account and project to equal the chosen values and run `gcloud projects describe "$PROJECT_ID" --account="$SA_EMAIL" --project="$PROJECT_ID" --format=json`. A successful read with the expected project ID proves authentication. Read retries may allow ordinary IAM propagation; failed mutations do not justify automatic repetition.
8. Persist private `credentials.env` containing the same fields as the bundled helper: `CLOUDSDK_CONFIG`, `CLOUDSDK_ACTIVE_CONFIG_NAME`, `CLOUDSDK_CORE_ACCOUNT`, `CLOUDSDK_CORE_PROJECT`, `GCLOUD_CONNECTOR_ACCOUNT`, `GCLOUD_PROJECT`, `GOOGLE_CLOUD_PROJECT`, `PROJECT_ID`, and `GOOGLE_APPLICATION_CREDENTIALS`. Preserve existing files. Record exact ownership in `connection.json` with `account`, `project`, and `role`.
9. Recheck the original account, project, active configuration, configuration files, and ADC are unchanged. Report only the verified connection scope. Run the bundled helper check against the exact saved key and ownership record; it does not adopt accounts from global CLI state.

For partial or legacy setup, first establish ownership of every saved file and remote identity. Preserve uncertainty for review. Do not remint keys, remove privileged bindings, switch a personal account, or overwrite credentials as a generic resume strategy.

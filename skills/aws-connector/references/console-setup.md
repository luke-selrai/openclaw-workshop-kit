# Console route without an existing CLI provisioning login

Use the isolated browser and intended account's IAM Users page. Create a fresh unique `claude-connector-<random suffix>` user, no Console password. A namesake is a collision, not permission to reuse it. Add an ownership tag `claude-connector` whose value is the exact new username. Attach only AWS-managed ReadOnlyAccess; do not alter another user's existing policies. Record its exact ARN/account and ownership privately.

Before creating an access key, verify the harness has a private capture route: owner-only artifact directory before showing credentials, mode-600 destination, no secret in tool responses, and cleanup of only the task's own credential-bearing snapshots/downloads. If this cannot be demonstrated, stop at that capture capability gap before creating the key. Do not use shared clipboard or ask for a key in chat.

In Security credentials, create one access key using the CLI/local-code use case. Save the one-time response directly to protected storage. Existing keys, key limits or a lost response require review; never delete a key based on age/last-used text or recreate automatically.

Use dedicated AWS credentials/config files inside a new mode-700 connector directory, never `~/.aws/credentials` or `~/.aws/config`. Keep subsequent operations in a process-local environment that selects these files and clears conflicting AWS credential/endpoint variables. Verify the exact created ARN with STS and a real IAM user read, expected read-only policy and absence of extra groups/inline policies before reporting success. The CLI helper's `finish` requires its own verified creation-stage records; do not manufacture those records for a Console-created identity. Record this separate route's proof and private file paths accurately.

If a supported existing-profile sign-in becomes available, prefer the scoped helper for a fresh attempt only after accounting for all state already created. Never create a duplicate identity merely to switch routes.

For this Console route, preserve the intended original config/credentials paths and hashes before setup in a private `console-original.json`. Record the newly created user/account/ARN, ownership tag and expected ReadOnlyAccess in a private `console-connection.json` only after the following proof succeeds. Keep this record separate from the helper's `connection.json` and stage markers.

Use a child process with inherited AWS credentials/profile/endpoint overrides removed, `AWS_EC2_METADATA_DISABLED=true`, `AWS_MAX_ATTEMPTS=1`, and `AWS_CONFIG_FILE`/`AWS_SHARED_CREDENTIALS_FILE` pointing at the dedicated connector files. Disable `cli_history` in its config and select that private store's `default` explicitly. Verify exact account/ARN with STS, then `iam get-user` for the exact created name and ownership tag. Confirm attached policies are exactly ReadOnlyAccess, inline policies and groups are empty, and `iam list-access-keys` contains exactly the one saved active key. Verify the original configuration hashes are unchanged. Do not report connected from Console creation or saved credentials alone.

On later invocations, repeat this proof from the actual caller using the same private files and saved Console identity. All downstream operations use that isolated child environment. Never route Console state through the scoped helper, whose stage markers prove a different creation path. On Windows, verify owner-only ACLs before capturing a secret; POSIX mode bits alone do not establish privacy there. Partial Console state is preserved for inspection, not replaced by a second identity or key.

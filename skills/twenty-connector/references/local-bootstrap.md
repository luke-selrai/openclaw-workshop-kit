# Fresh local owner and connection

Use this branch only for a newly created, empty laptop instance from Step A.2 when creating its owner and workspace is already authorized. The harness runs the helper; the attendee does not need to enter a generated password. Existing instances and remote deployments keep the normal sign-in route.

Run `scripts/bootstrap_local.py` relative to this skill's directory with Python 3. Supply `--compose-dir` with the new stack's directory, `--url http://localhost:3000`, `--email` with the intended owner's email, and `--workspace` with the intended workspace name. Use the account and name already established in the conversation; ask only if either is unknown. The helper uses the ordinary signup, workspace activation, role creation, and key creation interfaces. It does not use development seeds or change server settings.

The helper currently supports the checked Twenty 2.38.0 server protocol. Its read-only preflight checks the actual running server version, matching server URL and loopback publishing, and zero users, workspaces, and API keys in that server's database. Unknown versions or nonempty instances use the normal browser route; do not relax the checks to make onboarding pass. The standard Docker image runs migrations but does not seed a demo owner/workspace. `twenty-app-dev` is a different image with development accounts.

The helper creates `~/.claude/twenty-local-owner/` with mode 700 and generated owner credentials and recovery records with mode 600. It never prints passwords or keys and refuses to replace this directory or `~/.claude/twenty-connector.env`. Only source credential files privately in a process; never return their contents to the conversation. Keep the owner's password available in its private file for later sign-in or transfer to the user's password manager through an authorized private route.

CAPTCHA, email verification, disabled password signup, and billing gates stop the helper before signup when advertised in public configuration. Any subsequent server rejection also stops immediately. Complete the normal verification or consent screen using the existing browser route; never change verification settings, environment mode, or database records to get past it. If a request fails after creating an account, keep the private state and resume that account through normal sign-in. Do not delete state to rerun signup or mint replacement keys automatically; a timed-out mutation may already have succeeded.

The generated connection key has a dedicated role that can read records but cannot update/delete records, change settings, or access all tools. It expires after 30 days. The helper stores it in `~/.claude/twenty-connector.env` only after successful authenticated company and people reads. On `CONNECTED_READ_ONLY`, skip browser key creation and report: “Your local Twenty workspace is connected. I can read its records.” Broader operations require an appropriate role change when the user actually requests them; do not promise write access from this read-only test.

If either read fails, the generated key remains privately saved for diagnosis. No success claim or duplicate signup follows. After success, the harness should also run Step 7 from the saved environment in its actual caller runtime. For this role, a metadata 403 is expected: Twenty protects those reads with Data Model settings permission, which also allows schema changes. Keep the key read-only. This branch uses that environment as its credential store; it does not need the credentials-only MCP stub in Step 5.

### Resume the known overlength-password rejection

An earlier helper generated a 52-character password, but the checked 2.38.0 server accepts 8–50 characters and rejects that password before saving a user. For this exact failure only, rerun the helper with the same arguments plus `--resume-rejected-signup`. The helper requires a private directory containing only `owner.json`, matching URL/email, the original generator's exact 52-character shape, no saved connector environment, and a fresh authoritative database check showing zero users, workspaces, and keys. It preserves the original file and writes `owner-retry.json` privately with the first 48 characters of the existing generated password before attempting signup once. No new random credentials are generated by this repair.

After this repair, **`owner-retry.json` is the active owner credential file** for later sign-in or authorized password-manager transfer; `owner.json` is retained only as the rejected original. Any additional state, existing user, timeout, or further rejection stops this shortcut. Preserve all files and resume through normal sign-in or diagnosis; do not remove files to make the guard pass. Errors expose only allowlisted public error codes and the operation name, never server messages, passwords, or returned credentials.

## Protocol evidence

The upstream [signup documents](https://github.com/twentyhq/twenty/tree/c8fc76650231ca3640276f75f071670b20e51e75/packages/twenty-front/src/modules/auth/graphql/mutations), [activation mutation](https://github.com/twentyhq/twenty/blob/c8fc76650231ca3640276f75f071670b20e51e75/packages/twenty-front/src/modules/workspace/graphql/mutations/activateWorkspace.ts), [role input](https://github.com/twentyhq/twenty/blob/c8fc76650231ca3640276f75f071670b20e51e75/packages/twenty-server/src/engine/metadata-modules/role/dtos/create-role.input.ts), and [key mutation](https://github.com/twentyhq/twenty/blob/c8fc76650231ca3640276f75f071670b20e51e75/packages/twenty-front/src/modules/settings/developers/graphql/mutations/createApiKey.ts) describe the ordinary `/metadata` interfaces used here. They were compared with the compiled auth, workspace, role, and key resolvers in the official 2.38.0 image, digest `sha256:6c95b4baf3fcd9746bb513514e058f6dee3da880594c348a9e61ae1619fbd6fd`. The checkout itself was already 2.39.0, so a checkout version alone is insufficient evidence about the running container.

The upstream `workspace:generate-api-key` CLI is restricted to development/test environments, always assigns Admin, and prints its token. It is not the custom-owner bootstrap route for the standard Docker image. Keep those restrictions intact.

The same deployed image's `dist/engine/core-modules/auth/auth.util.js` defines `PASSWORD_REGEX = /^.{8,50}$/`. In `services/sign-in-up.service.js`, `generateHash` enforces it while computing the user payload, before `saveNewUser`. The password-length fixture reproduces that rejection. Its compiled `MetadataResolver` decorator and auth resolver place `signUp` at `/metadata`; the endpoint and token selection were valid in the failed run.

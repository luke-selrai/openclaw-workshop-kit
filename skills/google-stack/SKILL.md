# Google stack - the door to Google's own 131 Agent Skills

Google publishes its own Agent Skills, Apache-2.0, in the same open format this kit
uses: 128 in `google/skills` (Google Ads, Google Analytics, Google Cloud, developer
tooling) and 3 in `google-gemini/gemini-skills` (the Gemini API). All 131 are
vendored verbatim in this skill's `pack/` folder. **This file is the only part that
is ever loaded on its own**; the pack costs nothing until one of its files is read.

Provenance, pinned upstream commits and the update script: `pack/PROVENANCE.md`.

## How the pack is read

```
this file          hot   - intent -> exact path, about one page
pack/<lane>/<skill>/SKILL.md   cold  - read by path when the job calls for it
```

- **Read, never install.** Open `pack/<lane>/<skill>/SKILL.md` with the Read tool
  and follow it. Do not copy anything out of `pack/` into `~/.claude/skills/`,
  and do not run `npx skills add google/skills` or the plugin install the upstream
  README offers: that would put 131 descriptions into every session, which is
  exactly what this layout avoids.
- **Paths are relative to this skill's folder** (`~/.claude/skills/google-stack/`
  once installed; `skills/google-stack/` in the kit repo).
- **Finding one that is not in the tables below:** from this skill's folder,
  `grep -l -i "<keyword>" pack/*/*/SKILL.md`, or read the `description:` lines in
  the frontmatter of the candidates. Each description says what the skill does,
  when to use it and, usually, when not to. Shortlist at most three, read those.
- A skill may reference sibling files (`references/`, `scripts/`, `assets/`). They
  sit next to its `SKILL.md`; read them by the same relative path.

## The kit's own connectors come first

The pack is API reference. Connecting an account is the kit's job, and the kit's
connector skills already know which Google route to take.

| The user wants to… | Go to |
|---|---|
| Connect Google Ads, or run a report and the account is not connected yet | `google-ads-connector` (it installs Google's official Ads MCP server itself; `pack/ads/google-ads-api-mcp-setup/` is the reference behind that step, not a second install path) |
| Anything Gmail, Calendar, Drive, Docs, Sheets, Slides, Forms, Tasks or Chat | `google-workspace-connector` / `google-chat-connector`: Claude's built-in connectors first, the `gws` command-line tool for the gaps. The Workspace tool's own skills are generated by `gws generate-skills`, covered in that skill; none of them are in this pack |
| Sign a machine in to Google Cloud, or use a service account | `gcloud-connector` first, then `pack/cloud/gcloud/` for the command guardrails |
| Google Ads strategy, what to say, what to bid | The kit's `paid-ads` and `ad-creative` skills. The pack tells you how to *call* the Ads API, never what to spend |

## Lane 1 - Google Ads and Google Analytics (`pack/ads/`, `pack/analytics/`)

The lane most business owners will actually touch.

| When the job is… | Read |
|---|---|
| Call the Google Ads API at all - credentials, developer token, pick a client library, first "retrieve campaigns" script | `pack/ads/google-ads-api-quickstart/` |
| Work out why an account lost conversions, leads dried up, or impression share dropped | `pack/ads/google-ads-api-account-diagnostics/` |
| Install Google's own Google Ads MCP server (reference only, see the table above) | `pack/ads/google-ads-api-mcp-setup/` |
| Set up the Data Manager API - auth and client libraries | `pack/ads/data-manager-api-setup/` |
| Push offline conversions or purchase events back to Google | `pack/ads/data-manager-api-event-ingestion/` |
| Push a customer list or audience to Google Ads or DV360 | `pack/ads/data-manager-api-audience-ingestion/` |
| Pull GA4 reporting data - metrics, dimensions, custom reports | `pack/analytics/google-analytics-data-api-basics/` |
| Change GA4 properties, streams or settings by API | `pack/analytics/google-analytics-admin-api-basics/` |
| Ads inside a mobile app, or video ads (IMA SDK) - 8 skills | `pack/ads/google-mobile-ads-*/`, `pack/ads/ima-*/` (only for an app that sells ad inventory) |

**Money and data gate.** The two `data-manager-api-*-ingestion` skills upload real
customer data (hashed email, phone, address) to Google and can change what Ads
optimises against; the audience one also carries a "remove all" path that can wipe
a live audience. Run a non-`validate_only` ingest, or the clear path, only after the
user has named the destination account and confirmed it is the one they mean.

## Lane 4 - standby, read only when the job actually calls for it

One line each, so nothing gets scanned by accident.

- **GKE - 31 skills**, `pack/cloud/gke-*`. Clusters, autoscaling, networking,
  storage, cost, security, upgrades, TPU/GPU troubleshooting.
- **Vertex Agent Platform - 13 skills**, `pack/cloud/agent-platform-*`. Deploy,
  tune, evaluate, register and monitor agents on Google's platform.
- **Data platform - about 10 skills**: Spanner, Bigtable, data lineage, managed
  Airflow (`managed-airflow-*`), Workload Manager.
- **Observability - about 10 skills**: `cloud-logging-*`, `cloud-monitoring-*`,
  SLO alerting, networking observability, Security Command Center queries.
- **Well-Architected Framework - 6 skills**, `pack/cloud/google-cloud-waf-*`.
  Security, reliability, cost, performance, operations, sustainability. Useful as
  review lenses.
- **Security and identity**: `pack/cloud/iam-*`, `gke-*-security`,
  `detection-engineering-coverage-evaluation`.

## Guardrails on the whole pack

- **Spend.** Around a hundred of the cloud skills instruct an agent to run
  `gcloud … create`, `terraform apply`, `kubectl apply`, `bq rm`, GKE and Cloud SQL
  provisioning. Some build in their own "confirm with the user" step; most do not.
  Treat every provisioning or deleting command out of `pack/cloud/` as the user's
  call: name the resource, state the likely cost, wait for a yes.
- **Customer data.** See the money and data gate in Lane 1.
- **Long-lived keys.** `pack/cloud/agent-platform-migrate-from-ai-studio/` walks
  through creating a service-account key file and copying it to a machine. That is
  Google's documented pattern but a weaker posture than workload identity; prefer
  workload identity on real infrastructure, and never echo a key into the transcript.
- **Third-party, verbatim.** Google authored these. Never edit a file under `pack/`;
  a fix goes upstream or into this file. `pack/update.sh` overwrites the lot.
- **Doc-grade, not workflow-grade.** These are API references shaped as skills. When
  one contradicts something the user already has running, the user's working setup
  wins until proven otherwise.
- **The live catalogue is optional.** `pack/developers/finding-google-skills/` fetches
  Google's current index from GitHub and follows whatever it returns. The local pack
  is the same catalogue as of the date in `pack/PROVENANCE.md`; reach for the live
  one only to check whether Google has published something newer, and follow its own
  rules on verifying the fetch before trusting it.

## Updating the pack

```bash
skills/google-stack/pack/update.sh
```

Re-pulls both upstream repos, replaces the vendored tree and reprints the counts.
Then regenerate the kit's markers (`node scripts/audit-skills.mjs --write`) and, if
a lane's count or membership changed, make the same edit to the tables above.
